## Read this before executing any plan

**Drift detection does not use git in this repository.** There is exactly one
commit (`3ec213d`, "Initial commit from Create Next App") and essentially the
entire application lives in uncommitted working-tree state. `git diff 3ec213d..HEAD`
is therefore meaningless noise. Every plan instead inlines excerpts of the code
as it existed when the plan was written; the drift check is to open the cited
file and confirm the excerpt still matches. A mismatch is a STOP condition.

**Plan 001 comes first for a reason.** Before it lands there is no way to verify
anything: `npx tsc --noEmit` is the only green command in the repository,
`npm run lint` exits non-zero with 267 errors, and there are no tests at all.
Every plan from 002 onward has "run the tests" in its done criteria.

## Findings considered and rejected

Recorded so nobody re-audits them.

- **Audit-log diffs leaking password hashes** — they do not.
  `computeDiff` at `src/lib/audit.ts:11` already excludes `passwordHash`,
  alongside `createdAt`, `updatedAt`, and `id`. Only the live SSE broadcast was
  a problem, and only for other fields; that is plan 004. Plan 001 adds a
  regression test pinning the exclusion.
- **`src/components/ui/demo.tsx` importing a missing `lucide-react`** — it does
  not. The file was adapted to `@phosphor-icons/react`, which is a declared
  dependency. It is dead code (never imported), which is why plan 012 deletes
  it, but there is no missing-dependency bug.
- **`.env` or `prisma/dev.db` committed to git** — neither is tracked.
  `.gitignore:34` covers `.env*` and `git ls-files` confirms it. The real
  exposure is the build artifact and the backup zip, which plan 002 addresses.
- **The `exceljs` advisory chain (8 of the 12 high-severity `npm audit`
  findings)** — not worth fixing. `archiver`, `archiver-utils`,
  `brace-expansion`, `glob`, `minimatch`, `readdir-glob`, `zip-stream`, and
  `rimraf` all sit under `exceljs`, and the only remediation `npm audit` offers
  is downgrading `exceljs` from `^4.4.0` to `3.4.0` — an older major of the
  library behind every Excel export. Plan 011 takes the `next` bump and
  explicitly declines this. Revisit when `exceljs` ships an updated `archiver`.
- **`src/app/(main)/depot/DepotScene.tsx` (3,205 lines) refactor** — deliberately
  deferred, not rejected. It is the largest file in the repository by an order of
  magnitude and everything on the depot view flows through it, which makes it a
  genuine debt item. But it is L-effort with MED risk and there is currently no
  test that would catch a regression in it. Revisit after 001 lands and after
  characterisation tests exist for the scene's state handling. `ReportBuilderClient.tsx`
  (1,666 lines) is in the same category.
- **Adding a `middleware.ts` for route protection** — not needed. Page-level
  protection lives in `src/app/(main)/layout.tsx:12-13` and server actions gate
  individually with `hasPerm`. The two real gaps found (`/users` having no
  permission check, and `saveDashboardLayoutAction` accepting a caller-supplied
  scope) are fixed at the call site by plans 003 and 008. Middleware would add a
  second, parallel authorization surface rather than closing anything.
- **`announcementText` as an XSS sink** — it is not. It renders as a React text
  child at `src/app/(main)/layout.tsx:40` and is escaped. The only raw sink is
  the accent colour at `src/app/layout.tsx:41-47`, which plan 006 handles.

## Direction findings (options, not defects)

These are choices for the maintainer, deliberately not turned into plans. They
are recorded here so the reasoning is not lost.

- **Finish the role → permission migration.** `src/lib/perms.ts:64-75` keeps a
  `LEGACY` numeric-role fallback alongside the `AccessRole` permission system,
  and the numeric `role` is still the real authority in `isRoleAllowedToManage`,
  in `session.role !== 4` checks at `src/app/api/admin/backups/route.ts:26,43`
  and throughout `src/app/actions/backup.ts` and `tickets.ts`, and in
  `getRoleLevel`. Two parallel authorization systems is where the gaps behind
  plans 003 and 008 come from. Medium effort, high payoff — but it is a
  migration with real blast radius and deserves its own design pass.
- **Manovr approval notifications miss legacy-role users.**
  `src/lib/audit.ts:98-106` finds approvers with
  `accessRole: { permissions: { contains: "manovr.confirm" } }`, so anyone still
  on a numeric legacy role never receives an approval notification at all. Small
  fix, real operational consequence, and a symptom of the item above.
- **`ScheduledReport.recipients` promises more than the code does.**
  `prisma/schema.prisma:250` documents it as "ids or addresses", but
  `src/lib/scheduler.ts:104-107` only `parseInt`s personnel ids into in-app
  notifications. Either the comment or the code should change. Email delivery
  from an offline terminal is a real constraint — this warrants a spike, not a
  build.
- **No update path for the desktop build.** `package.json` sets
  `publish: null` and each installation keeps its own SQLite database in
  `%APPDATA%` (`main.js:10-14`). If more than one terminal ever runs this, there
  is no story for shipping fixes or consolidating data. Worth deciding
  deliberately before the fleet grows rather than after.
